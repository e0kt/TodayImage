# Phase 1 Data Model: 分群类型重置

**Feature**: `004-group-category-reset` | **Date**: 2026-09-17

仅列相对 001–003 的增量。`Category`、`CategoryIndex`、`Blocklist`、`GroupPermission` 均不变。

---

## Entity: ResetEpoch（新增）

某个 `(日期, 群, 类型)` 被重置过的次数。它是「重抽能拿到新图」的**唯一**实现基础。

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | `str` | `<群>|<类型>`，与每日记录键同源 |
| `count` | `int` | 该日该群该类型被重置的次数，从 0 起 |

**Validation rules**

- **V-EPO-1** — 键形如 `<chat_key>|<category>`，解析时只切**第一个**分隔符，
  使类型名中含 `|` 时仍能正确还原（与记录键切前两个分隔符同源）。
- **V-EPO-2** — 缺省为 `0`。没有记录 = 从未重置。
- **V-EPO-3** — 每次重置 `+1`，不设上限，同日可反复重置（FR-405）。
- **V-EPO-4** — 与每日记录同生命周期：写入时若 `date` 非今日，`resets` 与 `records` **一并**丢弃（FR-406）。
- **V-EPO-5** — 私聊不产生 epoch。私聊无绑定可重置（FR-403）。
- **V-EPO-6** — 类型与群键沿用既有归一化（去括号、`strip().casefold()`），
  使 `TodayImage重置【黑丝】` 与 `TodayImage重置黑丝` 命中同一个 epoch。

## Entity: DrawSeed（修改）

抽图种子，原为四段式，现按 epoch 有条件地追加第五段。

| epoch | 种子 |
|---|---|
| `0` | `{日期}:{用户}:{会话}:{类型}` —— **与现状逐字节一致** |
| `≥1` | `{日期}:{用户}:{会话}:{类型}:r{epoch}` |

**Validation rules**

- **V-SEED-1** — **epoch=0 时种子必须与改动前完全相同。** 否则本功能一上线就会把所有群当天的图
  静默换掉一遍 —— 一次无声的全局副作用。这是本功能最重要的兼容性约束。
- **V-SEED-2** — epoch 递增改变种子，使选取结果**很可能**不同。但这只是概率保证
  （约 `1-1/N`），**不足以**满足 FR-402 的 MUST —— 真正的保证来自 ResetExclusion。
  这是实现期的修正：规划时误以为换种子就够了。
- **V-SEED-3** — 种子仍然逐用户不同，因此重置后新一轮里不同用户之间依然各自独立（FR-407 的前提）。
- **V-SEED-4** — 种子不含时间戳。同一秒内两次重置必须产生两个不同种子，故用计数而非时间（research R1）。

## Entity: ResetExclusion（实现期新增）

某次重置清掉的图片集合，下一轮抽取时排除。

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | `str` | 与 ResetEpoch 同键：`<群>\|<类型>`（已归一） |
| `images` | `list[str]` | 上一轮已发出的图片路径 |

**为什么需要它（实现期发现）**：只换种子**做不到** FR-402 的 MUST。
两个不同的种子有约 `1/N` 的概率落回同一张图 —— 50 张图库下连抽几轮必然撞上，
表现为「重置了还是那张」。测试 `test_incrementing_the_epoch_usually_changes_the_chosen_image`
实测 5 个 epoch 只选出 4 张不同的图，正是这个概率事件。

**Validation rules**

- **V-EXC-1** — 重置时把被清除记录里的图片写入排除集；下一轮抽取从池子里剔除它们。
- **V-EXC-2** — 排除后池子为空（图库太小）时退回全量：宁可重复也不能没得发，与既有去重的退让规则一致。
- **V-EXC-3** — 与 `records`、`resets` 同生命周期、同一次原子写。
- **V-EXC-4** — 按 (群, 类型) 分别维护，互不影响。

## Entity: ResetResult（新增）

一次重置的结果，仅用于回复与日志。

| 字段 | 类型 | 说明 |
|---|---|---|
| `cleared` | `int` | 本次清除的绑定条数 |
| `epoch` | `int` | 递增后的代数 |
| `category_exists` | `bool` | 该类型在服务器上是否有对应文件夹 |

**Validation rules**

- **V-RES-1** — `cleared` 为 0 是**正常结果**，不是错误：当天本就无人抽过该类型（FR-413）。
- **V-RES-2** — 即使 `cleared == 0`，epoch 仍然 `+1`。否则「今天没人抽过 → 重置无效 → 稍后抽的人
  仍落在旧种子」会形成一个难以察觉的空洞。
- **V-RES-3** — `category_exists` 为假时照常执行，仅在回复中追加提示（FR-417）。
- **V-RES-4** — 结果只反映**本群**，不泄露服务器上有哪些类型（沿用 002 的不暴露契约）。

## Entity: DailyRecord（不变）

结构、键、每日清理规则均不变。重置只是**批量删除**满足 `(chat_key, category)` 的条目，
复用 `taken_images` 已有的同一套键解析逻辑。

---

## 状态流转

```text
TodayImage重置<类型>
  │
  ├─ 权限 user_pm > 1 ─────────────► 核心在 handler 之前拒绝（无回复）
  ├─ 私聊 ────────────────────────► 解释：该命令用于群聊
  ├─ 参数为空 ────────────────────► 用法提示
  │
  └─ 持 (群, 类型) 锁
        ├─ 读取当天记录
        ├─ 删除全部 chat_key 与 category 均匹配的条目 → cleared
        ├─ resets[<群>|<类型>] += 1                    → epoch
        └─ 一次原子写落盘（记录与 epoch 同写）
              └─► 回复 cleared（+ 类型不存在时的提示）

之后任何人再抽 ─► 种子带上 :r{epoch} ─► 选到新图 ─► 重新定桩（仍当日固定）
```

## Cross-entity invariants

- **I-401** — epoch=0 的 `(日期, 群, 类型)`，其抽图结果与本功能上线前逐字节一致。
- **I-402** — 清记录与 epoch 递增要么同时生效、要么都不生效（同一次原子写）。
- **I-403** — 私聊永不读写 epoch。
- **I-404** — 重置后的新一轮内，群中不同用户互不撞图（图片数 ≥ 人数时）。
- **I-405** — `resets` 与 `records` 始终属于同一天；跨日一并清除。
