# Feature Specification: 分群类型重置

**Feature Branch**: `004-group-category-reset`

**Created**: 2026-09-17

**Status**: Draft

**Input**: User description: "提供一个功能 重置当前群聊下某一今日图片类型的绑定 可以允许群聊中的其他人重新拿到新的图片 这个指令限定只有pm0或者pm1可以发布 命令为TodayImage重置<图片类型> 如TodayImage重置黑丝"

## Overview

今日图片在群里是**每人每天每类型固定一张**，到北京时间 0 点才重置。这条规则本身是想要的，但它没有留任何手动出口：
群里换了话题、抽到的图不合适、或者单纯想让大家再抽一轮，都只能等到第二天。

本功能给 master / superuser 一条命令：`TodayImage重置<类型>`，清掉**当前群**下**该类型**当天的全部绑定，
让群里每个人都能重新抽到一张**新的**图。

### 为什么这不是「删掉记录」那么简单

抽图用的是种子随机：`{日期}:{用户}:{会话}:{类型}`。四个分量在重置前后**完全不变**，
所以只删记录的话，每个人重新抽会拿到**和刚才一模一样的那张**，功能等于没做（已实测验证，见 research R1）。

因此重置必须同时让种子发生变化 —— 这是本功能真正的技术内容，也是最容易做错的地方。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 重置后全群拿到新图 (Priority: P1)

master 在群里发送 `TodayImage重置黑丝`。群里之前抽过 `今日黑丝` 的人，再发一次都会拿到**与刚才不同**的图；
没抽过的人正常抽。其它类型、其它群、私聊都不受影响。

**Why this priority**: 这就是功能本身。拿不到新图就等于没做。

**Independent Test**: 群里两个人各抽一次并记下图；master 重置；两人再抽，确认都变了。

**Acceptance Scenarios**:

1. **Given** 群 A 里 甲、乙 今天都抽过 `今日黑丝`，**When** master 发送 `TodayImage重置黑丝`，
   **Then** 机器人确认重置，且 甲、乙 再抽都得到**与之前不同**的图。
2. **Given** 重置刚完成，**When** 甲 连续再抽两次，**Then** 两次拿到**同一张**（重置只放开一次，不是取消当日固定）。
3. **Given** 群 A 重置了 `黑丝`，**When** 甲 抽 `今日白丝`，**Then** 白丝的绑定**不受影响**。
4. **Given** 群 A 重置了 `黑丝`，**When** 群 B 的人抽 `今日黑丝`，**Then** 群 B **不受影响**。
5. **Given** 群 A 重置了 `黑丝`，**When** 有人在私聊抽 `今日黑丝`，**Then** 私聊行为不变（本就不限次数）。
6. **Given** 同一天同一类型被重置**多次**，**When** 每次之后重抽，**Then** 每次都能拿到新图。
7. **Given** 重置后群里多人重抽，**Then**「同群不撞图」仍然成立 —— 新一轮里彼此仍不重复。
8. **Given** 跨过北京时间 0 点，**Then** 重置状态随当天记录一起失效，不影响新的一天。

---

### User Story 2 - 只有 master / superuser 能重置 (Priority: P1)

群管理员、群主和普通群友都不能重置。只有 `user_pm <= 1`（master 或 superuser）可以。

**Why this priority**: 用户明确指定了权限边界，而重置会影响全群所有人的当日结果，权限放宽是有实际后果的。

**Independent Test**: 分别用普通群友、群管理员、master 发同一条命令，只有最后一个生效。

**Acceptance Scenarios**:

1. **Given** 普通群友（`user_pm=6`），**When** 发送 `TodayImage重置黑丝`，**Then** 无任何效果。
2. **Given** 群管理员（`user_pm=3`）或群主（`user_pm=2`），**When** 发送该命令，**Then** 无任何效果 ——
   这一点与 `TodayImage允许` 不同，后者群管理员可用。
3. **Given** superuser（`user_pm=1`）或 master（`user_pm=0`），**When** 发送该命令，**Then** 重置成功。
4. **Given** 无权限者发送，**When** 之后检查存储，**Then** 记录**未被改动**。

---

### User Story 3 - 命令自身的可用性 (Priority: P2)

发命令的人能立刻看出发生了什么：清了几个人的绑定、类型写错了会被告知、在私聊里发会被解释。

**Why this priority**: 重置是「看不见」的操作 —— 不给反馈的话，发命令的人无法判断是生效了还是打错了字。

**Independent Test**: 依次发送正常、空参数、不存在的类型、私聊四种情况，确认四种回复都不同且可读。

**Acceptance Scenarios**:

1. **Given** 群里该类型有 3 条绑定，**When** 重置，**Then** 回复里包含**被清除的条数**。
2. **Given** 群里该类型当天一条绑定都没有，**When** 重置，**Then** 回复说明本来就没有需要重置的，而不是报错。
3. **Given** 参数为空（只发 `TodayImage重置`），**Then** 回复用法示例。
4. **Given** 类型名两侧带括号或空格（`TodayImage重置【黑丝】`），**Then** 与不带时等价。
5. **Given** 在私聊里发送，**Then** 回复说明该命令用于群聊、且私聊本就不限次数。
6. **Given** 类型在服务器上不存在，**Then** 照常执行（清 0 条）并提示没有这个类型的文件夹。

---

### Edge Cases

- **重置一个本群未授权的类型** → 照常执行。重置针对的是当日绑定，与授权与否无关；通常清 0 条。
- **重置后没人再抽** → 无副作用；状态随当天记录在次日一并失效。
- **同一秒内多次重置** → 幂等叠加，不产生损坏状态。
- **重置与他人正在抽图并发** → 不得出现「一半人用旧种子、一半人用新种子且互相撞图」的中间态。
- **类型名大小写 / 空格差异** → 与授权、索引使用同一套归一化。
- **重置时图库正好为空** → 命令成功（清除绑定），但之后抽图仍然静默（没有图可发）。
- **重置后重抽时图片数少于人数** → 「同群不撞图」按既有规则退回允许重复，不因重置而改变。
- **存储文件损坏** → 与既有每日记录一致：当作空表，重置得到 0 条，不抛异常。

## Requirements *(mandatory)*

### Functional Requirements

**重置行为**

- **FR-401**: 系统 MUST 提供 `TodayImage重置<类型>`，清除**当前群**下**该类型**当天的全部用户绑定。
- **FR-402**: 重置后，之前抽过的人再抽 MUST 得到与重置前**不同**的图（图库只有一张时除外）。
- **FR-403**: 重置 MUST NOT 影响其它类型、其它群、以及私聊。
- **FR-404**: 重置后每个人 MUST 重新进入「当日固定」状态 —— 重置放开的是一次重抽，不是取消当日固定。
- **FR-405**: 同一天同一类型 MUST 支持多次重置，每次之后都能拿到新图。
- **FR-406**: 重置状态 MUST 随当天记录在次日（北京时间 0 点）一并失效。
- **FR-407**: 重置后的新一轮 MUST 仍然满足「同群同类型不撞图」。
- **FR-408**: 重置与并发抽图 MUST NOT 产生不一致的中间状态。

**权限**

- **FR-409**: 该命令 MUST 限定 `user_pm <= 1`（master 与 superuser）。
- **FR-410**: 群主（2）与群管理员（3）MUST NOT 能执行 —— 与 `TodayImage允许` 的权限边界**不同**。
- **FR-411**: 无权限者发送时，存储 MUST NOT 被改动。

**命令可用性**

- **FR-412**: 回复 MUST 包含被清除的绑定条数。
- **FR-413**: 当天没有绑定时 MUST 明确告知，而不是报错。
- **FR-414**: 参数 MUST 容忍两侧括号与空白，并与既有类型归一化一致。
- **FR-415**: 私聊中使用 MUST 给出解释，而不是静默。
- **FR-416**: 参数为空 MUST 回复用法。
- **FR-417**: 类型在服务器上不存在时 MUST 提示，但不阻止执行。

### Key Entities

- **重置代数 (Reset Epoch)**：某个 (日期, 群, 类型) 被重置过的次数。参与抽图种子的计算，是「重抽能拿到新图」的实现基础。
- **每日绑定 (DailyRecord)**：沿用既有定义，不做结构性改动。
- **重置结果**：一次重置清掉了多少条绑定，用于回复。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-401**: 重置后，群里此前抽过该类型的每个人重抽都拿到不同的图（图库 ≥2 张时 100%）。
- **SC-402**: 重置后重复抽取仍然当日固定 —— 同一人连抽 5 次得到同一张。
- **SC-403**: 同一天连续重置 5 次，每次之后都能拿到与上一轮不同的图。
- **SC-404**: 其它类型、其它群、私聊在重置前后行为完全一致。
- **SC-405**: `user_pm >= 2` 的任何人都无法通过本功能改动任何存储。
- **SC-406**: 重置后新一轮中，群内不同用户之间不撞图（图片数 ≥ 人数时）。
- **SC-407**: 每种失败情形（空参数、无绑定、私聊、类型不存在）都给出彼此不同且可操作的回复。

## Assumptions

- **「重置」= 重新抽一轮，而不是「取消当日固定」**。用户说的是「重新拿到新的图片」，即再固定一张新的；
  若要彻底不固定，那是私聊已有的「不限次数」行为，不是本功能。
- **`pm0 或 pm1` 对应 GsCore 的 `user_pm <= 1`**，即 master 与 superuser。SV 设 `pm=1` 即可由核心直接拦下，
  不需要自写权限判断 —— 与 003 采用同一套机制，只是阈值更严。
- **仅群聊有意义**。私聊在 003 之后已是「不限次数、不写记录」，没有绑定可重置，因此私聊中仅作解释。
- 类型名归一化沿用 002/003 既有规则（去括号、`strip().casefold()`）。
- 重置不检查该类型在本群是否已授权：重置针对当日绑定，与授权是两件事。
- 不提供「重置全部类型」；用户要的是按类型重置。如需批量，应作为后续单独决定。

## Out of Scope

- 重置**其它群**或全局重置（命令只作用于发送所在的群）。
- 重置**单个用户**的绑定（粒度是「该群该类型的所有人」）。
- 撤销一次重置。
- 私聊的任何行为改动。
