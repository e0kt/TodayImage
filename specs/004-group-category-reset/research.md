# Phase 0 Research: 分群类型重置

**Feature**: `004-group-category-reset` | **Date**: 2026-09-17

来源：本机 GsCore 源码（`sv.py`、`handler.py`）、TodayImage 既有实现，以及针对种子行为的一次实测。

---

## R1. 只删记录是空操作 —— 本功能的核心难点

**结论**：重置**必须**同时改变抽图种子。单独清除每日记录**完全不起作用**。

**验证**（实跑，50 张图、两个用户）：

```text
重置前  A=33.png  B=20.png
已清除 2 条记录
重置后  A=33.png  B=20.png
A 拿到新图? 否 —— 又是同一张！
B 拿到新图? 否 —— 又是同一张！
```

**原因**：抽图走的是种子随机，种子为 `{日期}:{用户}:{会话}:{类型}`
（`tdi/daily_store.py::draw_seed`）。这四个分量在重置前后一字未变，因此
`pick_image(pool, seed)` 必然落回同一个下标。清记录只是让它**重新算一遍同样的结果**。

去重（`unique_per_chat`）也帮不上忙：它排除的是「别人已占用的图」，而重置把所有人的记录一起清了，
排除集合变空，池子回到全量 —— 第一个重抽的人尤其必然拿回原图。

**决策**：引入**重置代数（reset epoch）**：某个 `(日期, 群, 类型)` 被重置过的次数，参与种子计算：

```text
种子 = {日期}:{用户}:{会话}:{类型}           epoch 为 0 时（与现有行为逐字节一致）
种子 = {日期}:{用户}:{会话}:{类型}:r{epoch}   epoch ≥ 1 时
```

epoch 为 0 时种子保持原样，是为了让**未被重置过的群逐字节保持现有行为** ——
否则这个功能会把全网所有人当天的图都换掉一遍，那是一次无声的全局副作用。

**Alternatives considered**：

- **重抽时改用无种子随机**（像私聊那样）。能拿到新图，但会破坏 FR-404：重置后就不再当日固定了，
  等于把群聊悄悄变成不限次数。用户要的是「再固定一张新的」。
- **把已持有的那张图从池子里排除**。对单个用户有效，但需要在清除前把旧图记下来并长期保留，
  多次重置后会积累成一张越来越大的排除表；而且第二次重置时无法保证再次变化。
- **给重置打一个时间戳并混入种子**（而非计数）。可行，但同一秒内的两次重置会得到同一个种子，
  违反 FR-405；计数没有这个问题。

## R2. 权限：`pm=1` 恰好等于 master + superuser

**结论**：把命令注册在 `pm=1` 的 SV 上，核心会在处理函数之前拦下所有 `user_pm > 1` 的人。

**依据**：`_sv_authorized`（`handler.py:179`）判据是 `if user_pm > _sv.pm: return False`，
而阶梯为 `0=master, 1=superuser, 2=群主, 3=群管理员, 6=普通用户`（`sv.py:278`）。
故 `pm=1` 放行 0 与 1，拒绝 2、3、6 —— 正是用户指定的「pm0 或 pm1」。

与 003 是同一套机制、不同阈值：003 的授权命令是 `pm=3`（群管理员可用），本功能是 `pm=1`。
**这个差异是有意的**：授权决定「本群能看什么」，群主理应能管；重置会改变**全群所有人**当天已经拿到的结果，
外溢更大，所以收紧到机器人所有者。

**决策补充**：新开一个 SV（`今日图片-重置`, `pm=1`），而不是复用 003 的 `今日图片-群授权`(`pm=3`)。
把两个不同权限级别的命令塞进同一个 SV 做不到 —— 权限是 SV 级的，
若挂在 pm=3 的 SV 上再在处理函数里自查 pm，就会出现「两处权限判断」，正是 003 R1 明确避免的漂移来源。

**Alternatives considered**：挂在既有 SV 上、handler 内自查 `ev.user_pm <= 1`。
被否决：重复判断，且核心升级改阶梯时两处会不同步。

## R3. 重置代数存在哪

**结论**：存进 `daily_records.json`，与当天记录同一份文件、同一次原子写。

```json
{
  "version": 1,
  "date": "2026-09-17",
  "records": { "...": { "image": "...", "created_at": 0 } },
  "resets": { "<群>|<类型>": 2 }
}
```

**理由**：

- **生命周期完全一致**。重置代数只在当天有意义，而该文件已经实现了「写入时丢弃非当天数据」
  （`save_records`）。放在一起，FR-406 不需要任何新代码就成立。
- **原子性**。清记录与递增代数必须一起生效：若分两个文件，中间崩溃会留下
  「记录清了但种子没变」= 所有人抽回原图，恰是 R1 那个 bug 的复现。同一份文件一次 `os.replace` 即可排除。
- 体量极小，一群一类型一个整数。

键用 `<群>|<类型>`，与既有记录键同源；解析沿用 `parse_key` 的「只切前两个分隔符」策略，
使类型名中含 `|` 时仍可正确还原。

**Alternatives considered**：

- **单独的 `resets.json`**。生命周期要自己管，且丧失与记录清除的原子性。
- **放进 `group_permissions.json`**。那是权限文件、长期存在且不按日清理；把当日状态混进去，
  会让两者的清理策略互相冲突。

## R4. 并发与「同群不撞图」

**结论**：重置复用既有的 per-`(chat_key, category)` `asyncio.Lock`；重置期间抽图请求排队。

**理由**：抽图的读-改-写已经持这把锁（`resolve_daily_image`）。重置若不持同一把锁，
可能出现：某个协程已读到旧 epoch 的池子、重置随后落盘、该协程再用旧种子写入 ——
结果是一个人停留在上一轮而其他人进入新一轮，且两轮之间**不保证不撞图**（FR-408、FR-407）。
用同一把锁就把这个窗口消掉了。

「同群不撞图」本身不需要改动：它从当天记录派生，记录清空后排除集合自然为空，
新一轮在新种子下重新累积。

## R5. 回复该说什么

**结论**：回复包含**被清除的条数**；类型在服务器上不存在时追加提示；私聊给解释。

**理由**：重置是一个不可见的操作 —— 群里不会有任何可见变化，直到有人再抽。
不报条数的话，发命令的人无法区分「生效了」与「类型名打错了」。条数是最小且最有信息量的反馈。

**披露边界**：命令是 `pm=1`，回复中出现的类型名是发送者自己输入的，条数只是本群的计数。
不列服务器上有哪些类型，因此不触碰 002 建立的「不暴露图库」契约。

**Alternatives considered**：重置后主动在群里公告「大家可以重新抽了」。
超出请求范围，且会把一个管理动作变成群消息骚扰；发命令的人自己说更合适。

## R6. 与既有特性的相互作用

| 关注点 | 结论 |
|---|---|
| 私聊 | 不受影响。003 之后私聊不写记录，没有绑定可重置；命令在私聊中只作解释（FR-415）。 |
| 分群授权（003） | 正交。重置针对当日绑定，不检查授权；未授权类型通常清 0 条。 |
| 黑名单（002） | 不相关。重置不产生抽图。 |
| 每日重置时区 | 复用 `current_date(reset_utc_offset())`，与抽图同一日期口径（FR-406）。 |
| 会话判定 | 复用 `chat_context`，不用 `group_id` 判私聊 —— 频道型平台上那样判会出错。 |
| epoch=0 兼容 | 种子在未重置时逐字节不变，现有用户当天的图不会因本功能上线而改变。 |

## Resolved Technical Context

| 项 | 结论 |
|---|---|
| 语言 / 依赖 | 不变：Python ≥ 3.11，仅标准库 |
| 权限 | 新 SV `今日图片-重置`，`pm=1`，由核心拦截 |

| 测试 | stdlib `unittest`；种子变化、当日仍固定、多次重置、隔离性、权限均需覆盖 |
| 约束 | 未重置的群行为逐字节不变；私聊零改动；不得破坏同群不撞图 |
