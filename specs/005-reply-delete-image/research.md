# Phase 0 Research: 回复删图

**Feature**: `005-reply-delete-image` | **Date**: 2026-09-19

来源：本机 GsCore 源码（`bot.py`、`models.py`）、**生产日志实测**，以及既有 001–004 实现。

---

## R1. 适配器不会把被回复的图片给我们 —— 这是整个功能的约束来源

**实测**（`data/logs/`，真实回复事件）：

```text
raw_text='确实'   reply='大学真该开个课交一下怎么写PPT…'   reply_id='1553387824'
   image=None   image_list=[]   image_id=None
```

四条样本一致：回复事件里
- `reply_id` = 被回复消息的 ID ✅
- `reply` = 被回复消息的**文本** ✅
- `image` / `image_list` / `image_id` = **全空** ❌

**结论**：拿不到被回复的那张图本身，也拿不到它的 URL。
因此「哪一张」**只能**靠 `reply_id` 反查，必须在**发送时**就把「消息 ID → 文件路径」记下来（FR-502）。

**被否决的方案**：

- **按被回复图片的内容哈希去图库里比对。** 前提不成立 —— 根本拿不到那张图。
  即便拿得到，QQ 重编码后哈希也对不上。
- **按 `reply` 的文本认。** 抽图消息的文案是模板（如「你今天的黑丝来啦！」），
  同一类型所有人都一样，无法定位到具体文件。

## R2. 拿发送回执要付出什么

**结论**：`bot.send` 只有在 `wait_recall=True` 时才返回消息 ID；否则恒为 `None`。

`Bot.target_send`（`bot.py:238-565`）里只有三处 `return`：

| 行 | 返回 | 条件 |
|---|---|---|
| 269 | `None` | 提前退出 |
| 528 | `[] if _recall_requested else None` | **未请求回执 → `None`** |
| 561 | `ids` | 请求了回执且等到了 |

代价与风险：

- `RECALL_WAIT_TIMEOUT = 10.0`（`bot.py:53`）。适配器不回执时，**每次发图最多多等 10 秒**。
- 回执依赖适配器实现 `echo` 字段（`bot.py:206`）。本机日志里**没有任何 recall 相关记录**，
  说明该能力**从未被使用过，支持与否未知**。
- 核心有能力探测与熔断：连续超时 `RECALL_DISABLE_AFTER_TIMEOUTS` 次后 latch 为不支持，
  之后立即返回不再等待。所以 10 秒的代价是**探测期一次性的**，不会长期存在。

**决策**：抽图时以 `wait_recall=True` 发送，把返回的消息 ID 与文件路径记成一张短表。
拿不到 ID（适配器不支持）时**不**阻塞、不报错，只是本功能退化为不可用，并在回复里说明改用
`删除图片 <类型> <图片ID>`。

**Alternatives considered**：

- **默认不开回执，仅在需要时开。** 做不到 —— 需要的时刻（收到回复）在发送**之后**。
- **给每条抽图消息加一个可见的短 ID 后缀**，回复时人工带上。不依赖回执、100% 可靠，
  但破坏观感，且等于把图库的内部标识常态化地暴露在群里 —— 与 002 建立的「不暴露图库」相冲突。
  作为**兜底**保留在文档里（用既有的 `删除图片 <类型> <图片ID>`），不作为主路径。
- **给所有人加 10 秒延迟换取该功能。** 不可接受：为一个低频的纠错操作，拖慢每一次正常抽图。
  熔断机制使这一点可控，但仍需在实现中确保「拿不到 ID 绝不拖慢后续发送」。

## R3. 识别不确定时怎么办

**决策**：三级解析，任何一级不确定都**不删**。

1. **`reply_id` 命中回执表** → 唯一确定，可删。
2. **回执表没有该 ID**（适配器不支持 / 记录已过期）→ 退回「当日记录唯一性」：
   在该会话该类型下，若当天只有**一条**记录，则它就是那张；否则进入 3。
3. **多候选或零候选** → **不删**，列出候选的图片 ID，或提示改用 `删除图片 <类型> <图片ID>`。

**理由**：这是一个**不可逆**且**全局**的操作。误删一个文件影响所有群和今后所有抽取，
而"功能暂时不可用"只是不便。所以不确定时一律偏向不动作（FR-503、SC-502）。

第 2 级看似取巧，但覆盖了最常见的场景：小群里只有一个人抽过该类型，此时唯一性是真实的。

## R4. 「让抽到的人重新抽」直接复用 004

**决策**：不新造机制。删除后，对**每一条指向被删文件的记录**执行 004 已有的那套：
清记录 → 该 `(会话, 类型)` 的重置代数 +1 → 把被删文件加入排除集。

**理由**：004 已经解决了同一个问题的困难部分 ——
光清记录会让人用同样的种子抽回同一张，而代数与排除集保证"必定换一张"（004 research R1）。
这里的差别只是作用范围：004 是整个类型的所有人，这里是"持有某张图的那些记录"。

**跨会话**：图库全局，同一张图可能被多个群、多个用户抽到。因此要扫描**当天全部记录**，
凡 `image == 被删路径` 的都要处理，而不只是命令所在的那个会话（FR-507、SC-504）。
受影响的每个 `(会话, 类型)` 各自 +1 代数。

**顺带的好处**：被删文件进入排除集后，即便在缓存过期前又被扫描到，也不会被抽中（FR-509）。

## R5. 删除与记录清理的原子性

**决策**：**先删文件，再清记录**；文件删除失败则整个操作中止且不动记录。

**理由**：两者无法做成真正的原子（一个是文件系统、一个是 JSON），所以要选一个**安全的失败方向**：

- **先删文件后清记录**：中间崩溃 → 文件没了但记录还在 → 那些人抽到的记录指向不存在的文件。
  而既有逻辑对此已有处理（V-REC-3：记录文件不存在则重抽），所以这个中间态是**自愈**的。
- **先清记录后删文件**：中间崩溃 → 记录清了但文件还在 → 大家重抽，且**可能又抽回那张错图**。
  这正是本功能要消除的现象。

所以顺序是被失败模式决定的，不是随意的。

删除后必须**立即失效目录扫描缓存**（FR-511），否则 TTL 内该文件仍在候选池里。

## R6. 权限：默认群管理员，可收紧

**决策**：命令挂在 `pm=3` 的 SV 上；另提供配置项，可**收紧**到 `pm=1`。

**理由**：

初稿曾主张收紧到 master，论据是「删除影响所有群，而群管理员只对自己群负责」。
运营方指出这个论证漏了一半 —— **错标本身就是全局的**：

| | 影响范围 |
|---|---|
| 一张图被打错标签 | **所有群**都会发错 |
| 删掉这张错标的图 | **所有群**都被修复 |

也就是说，删除并不是把一个局部权限扩大到全局，而是**用一个全局操作去修复一个全局错误**。
能发现错标的人（通常就是在群里看到发错图的管理员）把它修掉，对所有群都是净收益。
按「影响所有群」来收紧权限，等于让错误比修复更容易扩散。

第二条理由也不成立：本部署中 `data/TodayImage/` 是从 Immich **导出的副本**，
文件名即 Immich 的存储 UUID，原图仍在 `~/docker/immich/library/upload`。
删除图库副本**不销毁原图**，重新导出即可恢复 —— "不可逆"这个前提在此不成立。

**保留收紧开关**的场景：图库即原始数据、删除确实不可恢复的部署（FR-513）。

**实现方式**：SV 的 `pm` 在注册时固定，无法按配置动态变化。
因此注册在 `pm=3` 的 SV 上，并在 handler 内按配置**可选地**收紧到 `pm<=1`。

> 这是本项目**第一次**在 handler 内自查权限 —— 003 R1 明确说过要避免。
> 这里的偏离是有意的：需求本身就是「阈值可配置」，而 SV 的 `pm` 是注册期常量，
> 两者无法同时满足。取舍是：SV 的 `pm=3` 定义**上界**（普通群友根本进不来），
> handler 内只做**收紧**、永不放宽到 SV 之外，且该判断集中在一个函数里由测试钉死。

## R7. 回执表存哪

**决策**：内存中的有界 LRU，**不落盘**。

| 属性 | 取值 |
|---|---|
| 结构 | `OrderedDict[消息ID, (文件路径, 类型, 会话, 用户)]` |
| 上限 | 若干百条，按 LRU 淘汰 |
| 生命周期 | 进程内；重启即失 |

**理由**：

- 用途是「刚发出去的图被回复」，时间窗以分钟计。跨天、跨重启的需求不存在。
- 落盘会引入又一个需要按日清理的文件，收益为零。
- 丢失是**安全的**：退回 R3 的第 2/3 级，最差就是提示改用 `删除图片`，不会误删。

**上限必要性**：抽图是高频操作，不设限的字典会随运行时间单调增长。

## Resolved Technical Context

| 项 | 结论 |
|---|---|
| 语言 / 依赖 | 不变：Python ≥ 3.11，仅标准库 |
| 识别 | `reply_id` → 内存回执表 → 文件路径；失败退回唯一性判断，再失败则拒绝 |
| 回执 | 抽图以 `wait_recall=True` 发送；拿不到 ID 时功能退化，不得拖慢发送 |
| 重抽 | 复用 004 的清记录 + 代数 + 排除集，作用于全部持有该图的记录（跨会话） |
| 顺序 | 先删文件后清记录（中间态自愈）；删除后立即失效扫描缓存 |
| 权限 | SV `pm=3` 粗筛 + handler 内收紧到 `pm<=1`，可配置放宽 |
| 存储 | 回执表仅内存有界 LRU；不新增落盘文件 |
| 约束 | 任何不确定一律不删；失败时图库文件数零减少 |
