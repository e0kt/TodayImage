# Phase 1 Data Model: 回复删图

**Feature**: `005-reply-delete-image` | **Date**: 2026-09-19

仅列相对 001–004 的增量。

---

## Entity: SentImageRef（新增，仅内存）

一条已发出的抽图消息与它所用文件的对应关系。**从回复反查的唯一依据。**

| 字段 | 类型 | 说明 |
|---|---|---|
| `message_id` | `str` | 发送回执返回的消息 ID，即键 |
| `image` | `str` | 该消息所用图片的**绝对路径** |
| `category` | `str` | 归一化后的类型名 |
| `chat_key` | `str` | 会话键 |
| `user_key` | `str` | 抽到它的人 |

**Validation rules**

- **V-SIR-1** — 只有 `bot.send(..., wait_recall=True)` 真的返回了 ID 才写入。拿不到 ID 时
  **静默跳过**，不得报错、更不得拖慢发送（R2）。
- **V-SIR-2** — 有界 LRU，超出上限淘汰最旧的。抽图是高频操作，不设限会单调增长（R7）。
- **V-SIR-3** — **仅内存，不落盘**。用途是「刚发出的图被回复」，窗口以分钟计；
  跨天跨重启的需求不存在，落盘只会多一个要按日清理的文件。
- **V-SIR-4** — 丢失是**安全的**：退回按当日记录唯一性解析，再不行就拒绝。绝不会因此误删。
- **V-SIR-5** — 一次发送可能返回多个 ID（平台把消息拆成多条），每个 ID 都指向同一个文件。

## Entity: DeleteResolution（新增）

一次「回复 + `删除<标签>`」的解析结果。**本功能最该被单独测试的部分** ——
它决定会不会删错文件。

| 字段 | 类型 | 说明 |
|---|---|---|
| `outcome` | `str` | `ok` / `not_found` / `ambiguous` / `tag_mismatch` / `not_a_draw` |
| `image` | `str \| None` | 仅 `ok` 时有值 |
| `candidates` | `tuple[str, ...]` | 仅 `ambiguous` 时有值，供人工二选一 |
| `actual_category` | `str \| None` | 仅 `tag_mismatch` 时有值 |

**解析顺序（三级退让，V-RES 系列）**

1. `reply_id` 命中回执表 → 唯一确定
2. 未命中 → 看该会话该类型当天的记录：**恰好一条**则采用
3. 零条或多条 → `not_found` / `ambiguous`

**Validation rules**

- **V-DRS-1** — 除 `ok` 外的**任何**结果都 MUST NOT 导致文件被删除（FR-503、SC-502）。
  这是一个不可逆且全局的操作，不确定时一律偏向不动作。
- **V-DRS-2** — 解析出的文件所属类型与命令里的标签不一致 → `tag_mismatch`，不删（FR-504）。
  防的是「看错了图，删错了类型」。
- **V-DRS-3** — `reply_id` 为空（根本不是回复）→ `not_a_draw`。
- **V-DRS-4** — 五种 outcome 必须彼此可区分，对应五种不同回复（SC-507）。
- **V-DRS-5** — 标签归一化沿用既有规则（去括号、`strip().casefold()`）。
- **V-DRS-6** — 解析是**纯函数**：输入 `reply_id`、标签、回执表快照、当日记录，输出结果。
  不触碰文件系统，因此可穷举测试。

## Entity: DeleteOutcome（新增）

实际执行删除后的结果，用于回复与日志。

| 字段 | 类型 | 说明 |
|---|---|---|
| `image` | `str` | 被删文件的绝对路径 |
| `file_removed` | `bool` | 文件是否真的被删掉（可能本就不存在） |
| `records_cleared` | `int` | 被清理的当日记录数（跨会话） |
| `chats_affected` | `int` | 受影响的不同会话数 |

**Validation rules**

- **V-DOC-1** — 执行顺序**必须**是先删文件、再清记录（R5）。
  中间崩溃留下「文件没了但记录还在」，既有逻辑会自愈（记录指向的文件不存在 → 重抽）；
  反过来则可能让人**又抽回那张错图**，正是本功能要消除的现象。
- **V-DOC-2** — 文件删除失败（权限、只读）→ **整个操作中止**，记录一条不动（FR-510）。
- **V-DOC-3** — 文件本就不存在 → `file_removed=False`，但**仍然**清理记录，
  让人能重抽（US2 AS4）。
- **V-DOC-4** — 必须扫描**当天全部记录**，凡 `image` 等于被删路径的都处理，
  而不只是命令所在的会话 —— 图库全局，别的群可能抽到同一张（FR-507、SC-504）。
- **V-DOC-5** — 受影响的每个 `(会话, 类型)` 各自 +1 重置代数，并把被删文件加入其排除集
  （复用 004 机制，R4）。
- **V-DOC-6** — 删除后 MUST 立即失效目录扫描缓存，否则 TTL 内该文件仍在候选池（FR-511）。
- **V-DOC-7** — 按**完整路径**删除，不按 8 位短 ID —— 短 ID 由文件名派生，
  不同子目录下可能重复（V-IMG-5）。

## 复用：ResetEpoch / ResetExclusion（来自 004）

本功能不新造重抽机制。删除后对每个受影响的 `(会话, 类型)`：

| 动作 | 来源 |
|---|---|
| 清掉指向该图的记录 | 004 `reset_group_category` 的同一套键解析 |
| 代数 +1 | 004 ResetEpoch |
| 把被删图加入排除集 | 004 ResetExclusion |

**为什么必须三件一起做**：004 research R1 实测过，光清记录会让人用同样的种子**抽回同一张**。
这里那张图已经被删，会退化成「抽到不存在的文件 → 静默」，把错标问题变成"今天没图"问题。

## 状态流转

```text
回复某条消息 + 「删除<标签>」
  │
  ├─ user_pm > SV.pm(3) ──────────► 核心拒绝（无回复）
  ├─ 未达配置要求的阈值（默认 pm<=1）► 拒绝并说明
  │
  ├─ 解析（纯函数，不碰文件系统）
  │     ├─ not_a_draw / not_found / ambiguous / tag_mismatch ─► 拒绝，**零删除**
  │     └─ ok → image
  │
  ├─ 删除文件 ── 失败 ─────────────► 中止，记录不动（V-DOC-2）
  │                └─ 不存在 ──────► 继续清记录（V-DOC-3）
  │
  ├─ 扫描当天**全部**记录，凡指向该图的：
  │     清记录 + 该(会话,类型)代数+1 + 加入排除集
  │
  ├─ 失效目录扫描缓存
  └─► 回复：删了哪张、影响几条记录几个会话
```

## Cross-entity invariants

- **I-501** — 任何非 `ok` 的解析结果下，图库文件数不变。
- **I-502** — 删除成功后，该图片不可能再被任何人抽到（文件已删 + 在排除集里）。
- **I-503** — 持有该图的**每一条**当日记录都被清理，无论属于哪个会话。
- **I-504** — 回执表的丢失永远不会导致误删，只会导致功能退化为拒绝。
- **I-505** — `daily_records.json` 里不存在「指向已删文件且未被清理」的持久记录。
